Endgame Tables

How ddfast answers the last tricks of a deal from precomputed tables: every 2-card and 3-card ending is a single lookup, and 4-card endings are matched against a large table of learned card patterns.

Excerpts are from tables.hpp (the table layouts and the probes, which inline into the search) and src/solver.cpp. The examples were checked by running the real probes on the real tables. Figures come from docs/LOO.md (one Zen 5 core) and README.md.

Where the tables sit in the search

ddfast asks yes/no questions: "with this leader, does North-South take at least t of the remaining n tricks?" At every lead node, before generating any moves, it tries to settle the question cheaply, in this order:

1 card

Play the trick out directly: four cards, one winner.

2 cards

One lookup in the 2-card table. Always exact.

3 cards

One lookup in the 3-card table. Always exact.

4+ cards

The per-deal transposition table, then DDS's quick-tricks and later-tricks bounds.

4 cards

The 4-card pattern table. A hit is copied into the per-deal table, where it is cheaper to find again.

otherwise

Search: generate the leads and recurse.

if (n == 2 && g_use2) return probe2<NT>(H, L, all, target, R);

src/solver.cpp, lead()

Like every node of the search, a probe returns the answer and R, the cards that decided it. R is widened to every card above them in their suit (fill_up), and the parent folds it into the pattern it stores. So the tables do more than end the search two or three tricks early: they hand back small sets of relevant cards, which make the patterns above them more general.

What all three tables share

  • Leader-relative. A probe sees the four hands from the leader's seat and answers for the leader's side, so one entry serves all four leaders.
  • Compressed over the cards in play. The cards still in play are packed together with pext, so only which ones are higher matters, not their ranks. Two bit strings over those packed cards give each card's owner: one is set for the leader's left- and right-hand opponents, the other for partner and the right-hand opponent.
  • Trumps in a fixed lane, side suits sorted. ddfast always keeps trumps in lane 3. The 3-card and 4-card tables also sort the three side suits by length with a byte shuffle (shuf8), so endings that differ only in which side suit is which share one entry.
  • Cards that mattered are stored. Each answer comes with its set of deciding cards: the smallest exact set in the 2- and 3-card tables, and the set the search proved in a 4-card pattern.
const u64 h3 = H[(L + 3) & 3];
const u64 alls = ddport::shuf8(all, ctl);               // side suits sorted by length
const u64 ews = ddport::shuf8((H[(L + 1) & 3] | h3), ctl);
const u64 sws = ddport::shuf8((H[(L + 2) & 3] | h3), ctl);
const ddport::BitMask am(alls);
const unsigned lo = unsigned(am.ext(ews)), hi = unsigned(am.ext(sws));

2 cards: every ending, in memory

Eight cards, two per hand. The index is the suit-length composition of the eight cards, the strain, and the arrangement: which 4 of the 8 cards the opponents hold (C(8,4) = 70), which 2 of those are the right-hand opponent's (6), and which 2 of the leader's side's are partner's (6). That gives 70 × 6 × 6 = 2,520 arrangements. Each entry holds, for both targets, the answer and the 8-bit set of cards that mattered.

const unsigned rank = g_r70[lo] * 36 + g_r6[ddport::pext16(hi, lo)] * 6 + g_r6[ddport::pext16(hi, lo ^ 0xFF)];
const unsigned comp = g_comp[popc(all & LANE(0)) + 9 * popc(all & LANE(1)) + 81 * popc(all & LANE(2))];
const uint16_t e = g_t2[((comp * 2 + NT) * 2520 + rank) * 2 + (tl - 1)];
R = fill_up(am.dep(e & 0xFF));

tables.hpp, probe2. The second pext ranks the right-hand opponent's cards among the opponents' four; the third ranks partner's among the leader's side's four.

The table is 3.3 MB and is built in memory by every init() in a fraction of a second. Each stored set of mattering cards is the smallest exact one: every set of top cards was checked against all endings with the same suit lengths.

3 cards: every ending, on disk

Twelve cards, three per hand: C(12,6) × C(6,3) × C(6,3) = 924 × 20 × 20 = 369,600 arrangements, for each of 102 suit-length configurations (side suits sorted) and both strains. Five bytes per ending: the leader's side's tricks in 2 bits, then for each target 1 to 3 the 12-bit set of cards that matter. The file t3_v2.bin is 377 MB. A probe is one prefetched 5-byte read.

The deciding sets are what make a lookup useful to the search above it. "At least one trick" depends only on who holds the ♦A, so the result the parent stores holds for any placement of the other cards. Three tricks with the king onside depend on the ♠A, K and Q, and on the ♦A for the entry; the low cards do not matter.

4 cards: a table of learned patterns

A complete 4-card table would be far too large, so the 4-card table is not complete. It holds patterns: each one is a true statement about a whole class of endings with the same suit lengths in all four hands, naming only the owners of the cards that mattered and a bound on the leader's side's tricks. The patterns are learned when the table is built: random 6-card endings are solved for a fixed time, and every pattern proved for a 4-card ending along the way is kept. The table is then read-only.

  • Key: the suit lengths of all four hands, leader-relative, side suits sorted, and the strain. A directory maps the key to a run of groups of 8 entries, most-hit first.
  • Entry: a, the owners of the cards that mattered (the two owner bit strings, compressed); b, those cards, with 3-bit lower and upper bounds in bits 56-58 and 59-61.
  • Match: an entry decides the question when (b & own) == a and its bounds settle the target. Eight entries are tested at once (ddport::pmatch8: AVX-512 on x86, Google Highway on Apple silicon), and groups are prefetched 8 at a time.
  • Size: p4_v5.ent and .idx, 758 MB, read into memory at load time.
for (int j = 0; j < groups; j++) {
  ...
  const unsigned kd = ddport::pmatch8(ea + 8 * j, eb + 8 * j, q.own, tl);

Three of the four questions are answered by patterns. The fourth (South's side can in fact take all four tricks) has no pattern, so the search plays that ending out. Below it, every 3-card ending is a single lookup. With the king offside, the table answers all four questions, including "no" to four tricks.

What the tables are worth

With the tables turned off, the endings are searched instead. On the 600-deal public set, one Zen 5 core:

Turned offNodesSlowdownSource
Both: 3-card and 4-card tables+56%1.30×LOO
3-card table alone+7.3%1.04×LOO
4-card pattern table alone+7.5%1.03×LOO
4-card hits not copied into the per-deal table−0.5%1.04×LOO

The tables stand in for each other. Without the 3-card table, the 4-card patterns, the per-deal table and the bounds still catch most of the endings it would have answered, and the other way round. Only with both gone does the search grow by half. The tables matter even more for small positions: the README measures ddfast at 13× DDS's speed on 7-card positions and 58× at 5 cards.

Building them

The first init() builds whatever is missing, whatever it is asked to solve: the 3-card table in about 10 seconds (on 8 cores) by solving every 3-card ending, then the pattern table in up to 170 seconds on all cores, using up to about 5 GB of memory. The files go to the directory given to init(), or the default described in the README. Because the pattern table is filled for a fixed time, tables built on different machines can differ in size; the answers are exact either way, since every pattern is a proved statement (README).

Reimplementing it

  • Make every node return the cards its answer depended on, and store minimal sets in the tables.
  • Index endings leader-relative, compressed over the cards in play, with trumps in a fixed lane and the side suits sorted by length.
  • Store small endings completely (here 2 and 3 cards); above that, store learned patterns, not positions.
  • Expect overlap: each table alone is worth 3-4% here, the pair 30%.
